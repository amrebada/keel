Your AI writes YAML.
Keel runs the backend.

Keel is an open-source Rust backend built from ready-made plugins, such as sign-in, roles or a CRUD API. Your assistant reads a short manifest, writes a few lines of YAML, and only writes code for what is truly yours.

Build your first app → Read the docs 
# Example: sign-in, team roles and a tasks API,
# on Postgres with a Redis cache.
app: team-tasks
providers:
  db:    { use: postgres, url: "${secret:DATABASE_URL}" }
  cache: { use: redis,    url: "${secret:REDIS_URL}" }

plugins:
  - use: saas-auth@^1
    config:
      social: [google]
      roles:
        owner:  { permissions: ["projects.*"] }
        member: { permissions: ["projects.read", "tasks.*"] }
  - use: resource
    config:
      resources:
        tasks:
          scope: tenant
          cache_ttl: 30
          fields:
            title:  { type: string, required: true }
            status: { type: string, enum: [todo, doing, done] }
            due:    { type: date }

The problem

Every AI-built backend starts by rewriting the same 800 lines.

Sign-up, password reset, OAuth callbacks, role checks, pagination, Stripe webhooks. Each new project, your assistant generates them again, burns context reading them back, and quietly gets a security detail wrong.

Then come the steps no code can do: create the Google OAuth app, paste the Stripe key, add the webhook URL. Nobody tracks them, so the app breaks in production.

Keel turns all of that into tested plugins with a tiny contract an AI can read, and a ledger of every setup step that is still missing.

How it works

Describe, configure, run.

Three steps an assistant can do in a handful of calls, through the CLI or the built-in MCP server.

  1. 01

    Read the manifest

    Each plugin ships a short plugin.yaml: config, routes, events, permissions and setup steps. The AI reads a few lines instead of a codebase.

    $ keel plugins describe auth-oauth --ai
auth-oauth 0.1.0: Social login (OAuth2/OIDC)…
needs:   plugins: auth-core ^0.1
secrets: OAUTH_GOOGLE_CLIENT_ID, …
routes:  GET /auth/oauth/{provider}/start, …
setup steps: 7
  2. 02

    Write app.yaml

    It adds plugins and config, validated against each plugin's JSON Schema. Every problem comes back with its exact path.

    $ keel add auth-oauth
added auth-oauth@^0.1 to app.yaml
$ keel config validate
error: 1 problem(s) found
  - plugins[1].config.password_min_length:
    4 is less than the minimum of 8
  3. 03

    Track what is left

    Keys and console clicks become tracked setup steps. Routes they block answer 503 setup_incomplete until they're done.

    $ keel setup status
setup: 0 of 1 done, 1 missing
  TODO auth-core/jwt-secret
    1. Generate 32+ random bytes
    2. Store it as AUTH_JWT_SECRET
    next: set AUTH_JWT_SECRET

Batteries, as plugins

Everything a SaaS backend needs.
Nothing your AI has to regenerate.

Auth that's already right

Email and password with Argon2id, verification, magic links, rotating refresh tokens with reuse detection, TOTP two-factor, and social login on one OAuth2/OIDC engine.

GoogleAppleGitHubMicrosoftLinkedInFacebookXEmail + MFA

Roles and guards

Roles with inheritance and per-tenant grants. Put guards and validation in front of any route.

routes:
  /admin/**:
    guard: [authenticated, "role:admin"]
  "POST /projects":
    guard: ["permission:projects.write",
            "rate-limit:30/min"]

CRUD from a model

Describe fields. Get tables, migrations and REST with filters, sorting, paging, per-owner or per-tenant rows and caching.

GET/api/tasks?status=todo&sort=due
POST/api/tasks
PATCH/api/tasks/{id}
DELETE/api/tasks/{id}

Setup tracker

Every key, console click and webhook a plugin needs, with instructions. Nothing silently missing in production.

  • Create JWT signing key
  • Create Google OAuth client
  • Add Stripe webhook endpoint
  • Verify sending domain

Swap infrastructure in YAML

SQLite, Postgres or MySQL. Memory or Redis for cache and key-value. Secrets from env, .env or Vault.

sqlite→postgres memory→redis .env→vault

Live operations, zero downtime

Enable, disable and reconfigure plugins on a running server. Swap in a new binary under load, with automatic rollback if health fails. Every change lands in an audit log.

12:04:11apply billing-stripe enabled
12:04:12migrate billing_stripe/001_init
12:09:40swap v1.0.3 → v1.0.4, 0 dropped
12:09:43rollback health failed, back to v1.0.3

Safe migrations

Plugin migrations are checked first. Drops and renames are blocked unless you allow them by name, and touched tables are backed up.

blocked resource/tasks_12_drop
  drops column tasks.assignee
  allow with --allow resource/tasks_12_drop

Plugin catalog

Compiled in. Turned on by one line.

Plugins are Rust crates with a manifest and a config schema. The host starts only what app.yaml lists, after checking versions, dependencies and route ownership.

auth-core

Accounts, sessions, tokens, verification, reset, magic links.

 auth-oauth

Seven social providers on one OIDC engine, safe account linking.

 auth-mfa

TOTP and recovery codes with replay protection and lockout.

 rbac

Roles, inheritance, grants and tenant scopes. Powers guards.

 resource

REST CRUD, migrations and caching from YAML models.

 billing-stripe

Plans, Checkout, portal, webhooks and a plan guard.

 saas-authbundle

auth-core, oauth, mfa and rbac from one small config.

 your-plugin

Implement the Plugin trait from keel-sdk and ship a manifest.
